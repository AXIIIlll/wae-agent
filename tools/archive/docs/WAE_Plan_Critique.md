# 規劃總檢視：問題點清單（對抗式審查）

> 檢視範圍（這幾輪先後定下的東西）：
> 1. `docs/WAE_Agent_Plan.md`（LLM Agent，M0–M6，Qwen3-0.6B，500MB）
> 2. `docs/WAE_Generic_AppSelection_Plan.md`（意圖→挑 App，無預設）
> 3. 每 App 一份「最小文檔」+ 全域索引的記憶倉庫（上一輪討論）
> 4. 既有實作現況（AgentRunner、舊管線、APK、模型）
>
> 目的：在動手前找出**衝突、過度樂觀、會造成錯誤行為**的地方。

---

## 0. 一句話總結

> 方向都對，但目前的規劃有 **7 個 P0 級問題**：
> 三個決策大腦並存、模型在裝置上佔兩份、驗證寬鬆會污染記憶、
> 「無預設」已被自己違反、「短劇 App 可能讀不到畫面」、
> App 選擇成功率過度樂觀、以及測試強依賴手機。
> **不先修這 7 個，後面的功能做得越多，行為會越亂。**

## 1. 跨規劃衝突（最需要先解）

### 1.1 三個「大腦」並存，入口沒有單一規則
- 舊管線：`decomposeCommandIntoLocalGoals`（快、確定、只認動詞）
- LLM Agent：`AgentRunner`（Planner + DecisionResolver + 驗證迴圈）
- 新規劃：**意圖解析 + App 選擇 + 記憶倉庫**（還沒實作）

目前 AssistActivity 的分流是「長度 ≥6 字就走 Agent」，會造成：
- 「打開 YouTube」這種明確指令被送進慢速 Agent
- 「我想看劇」跟「幫我把藍牙關掉」走同一條路，但前者需要「選 App」、後者不需要
- 三套機制對「成功」的定義不一致

**問題**：沒有唯一的「Intent Router」，行為會分叉、測試也無法收斂。

**修正**：
```
明確指令（動詞+對象，單一 App）→ 舊快速路徑（毫秒級）
目標/開放式（我想…/幫我找…）→ Agent 管線（含選 App）
兩者都不確定 → 反問
```
Router 用資料驅動的規則（動詞表 + 是否含目標性詞），不要用長度。

### 1.2 「無預設」已被自己違反，而且守門測試抓不到
- 上一輪已把「紅果短劇」寫進 `global_tw_cn_app_metadata.tsv`
- plan prompt 也加了「看劇→短劇」的例子
- 但 `NoAppSpecificCodeTest` 只掃 `.kt`、`AgentPromptGuardTest` 只掃 `assets/agent` → **TSV 與 prompt 例子都沒被擋**

**修正**：
1. 移除紅果那筆 metadata 與看劇 few-shot（改由語意挑選）
2. 守門測試擴充：`assets/` 全域不得出現「App 名 ↔ 意圖」的對應（至少不能有人工寫死的 App 別名到意圖）
3. 在文件中明確定義「事實資料」與「流程預設」的差別

### 1.3 500MB 預算 vs 裝置實際佔用
- APK：481.5MB
- App 首次使用會把 **350MB GGUF 複製到 filesDir**（實測 emulator 已複製 367MB）
- 加上 sherpa 模型 ~35MB、ONNX 模型 ~42MB、TSV…
- **實際佔用 ≈ 830–900MB**，是「500MB 計畫」的兩倍
- 使用者的手機曾是「125MB + 115MB 就抱怨」的狀態

**修正（選一）**：
- A. 不複製模型：llama.cpp 直接從 APK asset 的 FD 載入（需要 `/proc/self/fd/N` 路徑或改 JNI 用 mmap 讀 fd）
- B. 保留複製，但在文件與 UI 明確標示「安裝後約多佔 350MB」
- C. 模型放 external files 且可刪（下載式；但違反「零下載」）

### 1.4 「成功」的定義不一致（會污染記憶）
- `AgentLoop` 目前把 `UNCERTAIN` 也算成功（`verified = ok && outcome != FAIL`）
- 記憶倉庫規則卻要求「只記成功且驗證通過」
- 若把 UNCERTAIN 寫進記憶 → **記憶污染**

**修正**：
- 記憶寫入只接受 `OK`（嚴格），`UNCERTAIN` 只記錄「觀察」不升級
- 或把 `UNCERTAIN` 改成「重試一次再判定」，但絕不寫入記憶

### 1.5 記憶倉庫 vs 安全層的先後順序
- 規劃寫「AI 要什麼自己去找」，但沒定義：**記憶檢索出的候選要不要過 SafetyGate？**
- 若記憶裡記過「付款」按鈕，下次自動點下去就出事

**修正**：
- 記憶只提供候選；所有動作一律先過既有 SafetyGate/風險分級
- 不可逆動作永遠人工確認（沿用現況）

## 2. P0 問題（不修會出錯）

| # | 問題 | 為什麼嚴重 | 修正 |
|---|---|---|---|
| P0-1 | 模型佔兩份（APK+filesDir 350MB） | 使用者實際要多花 350MB | 見 1.3 |
| P0-2 | `UNCERTAIN` 算成功 | 記憶污染、報告虛高 | 見 1.4 |
| P0-3 | 三套決策並存、路由用「長度」 | 行為分叉、明確指令變慢 | 見 1.1 |
| P0-4 | 已寫死的「紅果短劇」+ 無守門 | 直接違反鐵律 | 移除 + 測試 |
| P0-5 | **短劇類 App 以影片/圖片為主，a11y 文字可能極少** | 「我想看劇→真的播放」成功率會被高估；規劃說 80–90% 只涵蓋「選對 App」，沒涵蓋「播放成功」 | 把成功拆兩級：開啟正確 App（可驗）vs 實際播放（需驗證器 + 可能用 OCR/截圖） |
| P0-6 | App 選擇準確率樂觀 | label 是英文/縮寫、category 常缺、中文 token 化不一定對得上 → 80–90% 只在「名稱有線索」時成立 | 先量測再承諾；把「驗證+換候選」當主路徑，不是補救 |
| P0-7 | 測試強依賴實體手機（而且你常拔） | 規劃的 P0/P1 也說「先做不用手機」，但 App 清單/畫面驗證最後仍要真機；沒有裝置就無法驗收 | 建立「無手機驗收集」：錄好的 UI XML/snapshot 離線重放；手機只做最後 smoke |

## 3. P1 問題（會讓體驗變差 / 難維護）

| # | 問題 | 說明 | 建議 |
|---|---|---|---|
| P1-1 | 延遲疊加 | 選 App 1 次 LLM + 規劃 1 次 + 每步決策；手機上可能 15–40 秒 | 選 App 用 embedding 為主（毫秒級），LLM 只在 Top-2 難以區分時才呼叫 |
| P1-2 | App 更新 / 伺服器端 UI 變更 | `versionCode` 不變但畫面變（Google 類 App 常 A/B） | 加 `lastVerified` TTL（例如 7 天）＋使用前驗證；TTL 過期降權 |
| P1-3 | index 與 per-app 文檔不同步 | 兩份資料要維護 | index 可由文檔掃描重建；寫入時 temp+rename 原子替換 |
| P1-4 | 併發寫入 | 多執行緒同時寫同一文檔 | 單一寫入佇列（memory writer）；或每 App 一個 mutex |
| P1-5 | 隱私 | UI 文字可能夾帶使用者內容（訊息、驗證碼） | 只存白名單欄位（viewId/class/role + 短 UI 標籤 ≤12 字），長文字/輸入內容一律不存 |
| P1-6 | `QUERY_ALL_PACKAGES` Play 政策 | 已存在此權限，Play 上架會被審 | 已決定側載；若未來上架需改用 package visibility 宣告 |
| P1-7 | 背景探索耗電 | 對常用 App 自動開起來掃 | 預設關閉、只在充電+閒置時；或直接不做，靠被動學習 |
| P1-8 | 中文語意校準 | MiniLM 對「短劇/追劇/看劇」vs App label 的相似度未實測 | 先做離線校準集（20 個意圖 × 30 個 App label），量 Top-1 |
| P1-9 | 學習資料污染 | 使用者改主意/誤點也會被記 | 只記嚴格成功；失敗降權；可一鍵清除 |

## 5. 規劃中「說得太滿」的地方（要改成有條件的承諾）

| 原句 | 問題 | 改成 |
|---|---|---|
| 「我想看劇 → 80–90% 一次選對」 | 只算選 App，不算播放 | 「名稱有線索時選對 80–90%；端到端播放需實測，預估 40–60%」 |
| 「P0/P1 不用手機」 | 仍需要真機 App 清單與畫面樣本 | 「P0 需要一次真機 snapshot 收集；之後可離線重放」 |
| 「APK 500MB」 | 沒算 filesDir 模型複製 | 「安裝後裝置佔用約 830MB（若不做 FD 直載）」 |
| 「AI 自己去找」 | 沒定義檢索失敗怎麼辦 | 「找不到 → 反問使用者；不得盲點」 |
| 「只記成功」 | 現行程式把 UNCERTAIN 當成功 | 先修 1.4 才成立 |

## 6. 修正後的執行順序（建議）

1. **定義 Intent Router**（明確指令 vs 開放目標）+ 移除長度分流
2. **修 `UNCERTAIN` 語意**（記憶只收 OK）
3. **移除紅果 metadata / 看劇 few-shot**，守門測試擴充到 TSV 與 prompts
4. **模型載入不複製**（或明確接受 +350MB 並在 UI 標示）
5. **App 選擇先做離線量測**（label 語意校準集，不需要手機）
6. **記憶文檔 MVP**：identity 文檔 + 被動記錄（只收嚴格成功）+ index
7. **選 App + 規劃接線**（embedding 為主、LLM 為輔）
8. 真機 smoke（一次性，收集 snapshot 後可離線重放）
9. 才做「短劇播放」端到端

## 7. 需要你決策的點

1. **模型載入方式**：直接 FD 讀 asset（省 350MB，但要改 JNI）還是接受 +350MB？
2. **記憶範圍**：只存「入口元素」還是連「畫面簽章」都存？（後者更準但更多內容）
3. **背景探索**：做（預設關）還是不做？
4. **成功定義**：「我想看劇」的驗收是開啟正確 App、還是必須真的開始播放？
5. **短劇 App 畫面讀不到時的 fallback**：OCR/截圖（要多接一個模型）還是直接反問使用者？

# 廣度 × 穩定度計劃（2026-11-17）

> 前提：智力（語言理解、世界知識）不可能贏 Apple／Google。
> 所以只拼兩件事：**所有 App 都能操作（廣度）** 與 **每次結果一致（穩定）**。
> 這個計劃裡**沒有任何新模板、沒有任何新框架、也沒有要訓練更大的模型**。

## 一、廣度：五類 App 的感知／操作通道

| App 類型 | 感知 | 操作 | 現況 |
|---|---|---|---|
| 原生（a11y 完整） | a11y 樹 | node click / setText | ✅ |
| WebView / Hybrid | a11y 稀疏 + OCR | node / 座標 | 🟡 OCR 剛接進 Agent |
| Flutter / Compose（自繪） | 幾乎沒有 a11y + OCR | 座標 | 🟡 |
| Canvas / 遊戲 / 影音 | 只有畫面 | 座標 + 手勢 | 🟡 |
| 系統設定（各 OEM） | a11y + 分類別名 | node | ✅（J） |

### 要補的四件事

1. **OCR 常態化**：現在只在「a11y 元素 < 6」時跑。要改成**目標找不到時也跑一次**
   （很多 App 有 a11y，但關鍵元素是圖片）。
2. **圖示型按鈕**：沒有文字的按鈕靠「可點區塊 + 位置先驗 + 圖示偵測」。
3. **捲動容器偵測**：找出哪個區域可捲（不是整個畫面亂滑）。
4. **OCR 輸入框**：沒有 node 的輸入框 → 點擊後用剪貼簿貼上（ImeHelper）。

## 二、穩定：六道防線

| # | 防線 | 現在 | 要補 |
|---|---|---|---|
| 1 | **確定性優先**：文字/角色唯一命中就不叫模型 | ✅ | — |
| 2 | **開跑前整備**：回首頁、等畫面靜止、關廣告/權限彈窗 | ✅ | 等 a11y 事件靜默 300ms |
| 3 | **每步驗證**：只有 TAP 造成的變化算成功；目標字串或音訊才算完成 | ✅ | — |
| 4 | **失敗恢復**：換候選 → BACK → 重試一次 → 反問 | 🟡 | 換候選（目前只 BACK 重挑） |
| 5 | **全域護欄**：步數/時間上限、無進展就停 | ✅ | 同一狀態不重複（visited） |
| 6 | **可回報／可回滾**：每步證據 JSON、失敗回到起點 | ❌ | 全部 |

### 新增：重跑一致性

- 模型推論一律 `temperature = 0`（禁止隨機）。
- 同一指令重跑 3 次，**路徑與結果必須一致**；不一致就視為 bug（時序或競態）。

## 三、量測（沒有數字就沒有穩定）

| 指標 | 怎麼量 | Gate |
|---|---|---|
| 類別覆蓋率 | 20 個 App × 5 類 × 3 指令 | ≥ 90% 類別能完成至少一項 |
| 成功率 | 120 題（EASY/MEDIUM/HARD） | 依階段訂 |
| 重跑變異 | 30 題各跑 3 次 | 成功率標準差 ≤ 5% |
| 每步延遲 | p50 / p95 | p95 ≤ 800ms |
| 失敗分類 | 感知 / 定位 / 驗證 / 逾時 / 反問 | 每類 < 20% |

## 四、里程碑

| 階段 | 內容 | 產出 |
|---|---|---|
| **M1（本週）** | OCR 常態化＋座標操作＋每步證據 JSON | 可操作「沒有 a11y 的 App」並能交出證據 |
| **M2** | 圖示按鈕、捲動容器、OCR 輸入框貼上 | 影音/遊戲類可操作 |
| **M3** | 穩定度 harness（300 次）＋失敗分類報表 | 一張「哪裡不穩」的熱圖 |
| **M4** | 依失敗分類逐項修到 gate 達標 | 穩定量測報告 |

## 五、明確不做

- 不做「更聰明的規劃」（那是他們的戰場）。
- 不為個別 App 加專屬模板。
- 不為了 demo 好看而犧牲可重現性。
- 不在 M1–M4 期間訓練新模型。

## 六、和模型計畫的關係

元素決策模型（Actor/Critic/Memory）**排在 M4 之後**，而且只有在
「M3 的失敗分類顯示『定位錯誤』占多數」時才值得做——因為那才是模型能救的部分。
若失敗主因是「時序/彈窗/捲動」，模型一點用都沒有，先把工程做穩。

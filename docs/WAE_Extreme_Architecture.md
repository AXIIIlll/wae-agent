# WAE 極限架構 v3：從「每步分類器」到「每步不必看」

> 版本：1.0（設計稿，尚未實作）
> 日期：2026-11
> 定位：在現有 V2.6 之上再往上推一層，目標是**用極低成本取得別人的高成本能力**。
> 原則：每一節都寫「極限版本」與「失敗時退化成什麼」，確保任何一項都能單獨關閉、單獨回退。

---

## 0. 一句話主張

> **別人比的是「每一步看得準」；我們要比的是「每一步不必看」。**

現有 V2.6 仍然是「每一幀重新感知 → 重新打分 → 選一個候選」的分類器架構。
分類器的成本與步數成正比（每步 200–600ms），而**編譯器的成本幾乎與步數無關**（查表 30ms）。

本文件的核心轉向：

```
分類器：state_t → 感知(200ms) → 打分(90ms) → 決策(30ms) → action_t      成本 O(N·320ms)
編譯器：{(state, action, state')}*  ──壓縮──▶  App 自動機  ──查表──▶  action_t   成本 O(N·30ms)
```

我們已經有的原料，是別人沒有的：**被動觀察 + 執行紀錄的三元組**
`(sigsBefore, action, sigsAfter, postcondition, 成功與否)`。
目前只被用來「重放單條鏈」，這是極大的浪費。

## 2. 核心轉向：三層取代一層

```
┌──────────────────────────────────────────────────────────────┐
│ L3' 規劃層 Planner    目標後置條件 → 圖上最短路（A*/D* Lite）  │
├──────────────────────────────────────────────────────────────┤
│ L2' 自動機層 Automaton 頁面狀態圖：節點=簽名、邊=動作+守衛     │
├──────────────────────────────────────────────────────────────┤
│ L4' 執行層 Executor    查表 → 派發 → 檢查點驗證 → 失敗回寫     │
└──────────────────────────────────────────────────────────────┘
         ▲                                          │
         └──────── 回寫：正邊（成功）／負邊（失敗）──┘
```

**與現有架構的關係**：這三層是「疊加」不是「取代」。當自動機命中時走新路徑；未命中時退回現有的分類器管線（L1→L3）。
因此**任何一步都可以只靠舊管線運作**，新層隨時可關閉。

## 3. 子系統 S1：App 自動機編譯器（核心）

### 3.1 形式定義

把每個 App 建模為一個帶守衛的轉移系統：

```
A_pkg = (S, A, T, s0, C)
  S  : 狀態集合，元素為「正規化頁面簽名」s
  A  : 動作集合（3 原語 × 細分碼）
  T  : 轉移集合 { (s, a, g, s', post, stats) }
        g    = 守衛（元素存在、能力可用、安全允許）
        post = 後置條件（可驗證的畫面性質）
        stats= 邊統計（成功次數/失敗次數/延遲分佈）
  s0 : 進入 App 的預設頁
  C  : 邊成本 c(s,a) = 延遲 + λ·(1 − 成功率)
```

### 3.2 節點：正規化頁面簽名（關鍵在「正規化」）

現有簽名 `pageSpineSigs` 是 256B 主幹節點雜湊集合，**直接當節點會爆炸**（同一頁的列表內容不同）。

**極限做法：三層正規化**

| 層級 | 做法 | 效果 |
|---|---|---|
| L-a 結構正規化 | 簽名只取「容器骨架」：class + 深度 + 子節點數，忽略文字 | 同頁不同內容 → 同一簽名 |
| L-b 集合化 | 用 **MinHash(64)** 表示簽名集合，估 Jaccard 為 O(1) | 比較成本從 O(n) 降到 8 個整數運算 |
| L-c 疊化（bisimulation） | 若兩狀態的**出邊標籤集合**相同且後繼等價 → 合併 | 圖節點數通常可降 5–20× |

**bisimulation 判斷**（實用版）：

```
s ≡ t  iff  { label(s,a) : a ∈ A } == { label(t,a) : a ∈ A }
            且所有對應後繼 s', t' 已在同一等價類
```

這是多項式時間的 partition refinement；以 500 節點的圖而言，單次重算 < 10ms。

**容量的極限做法**：節點與邊的預算**不是常數**，而是依 App 已觀測到的複雜度自我調整，
且完全由程式計算（無 AI、無隨機、可重現）。詳見 §3.7。

**極限目標**：預算內節點數始終 ≤ `nodeBudget(pkg)`，超過時依「重建成本」淘汰（§3.7.4）。

### 3.3 邊：動作 + 守衛 + 後置條件

```kotlin
data class AutomatonEdge(
    val from: Int,              // 狀態 id（MinHash 收斂後的節點）
    val to: Int,
    val op: FineOp,             // I:TAP / I:VAL / N:TXT …
    val selector: String,       // 選擇器鍵（viewId > 角色+文字 > 座標）
    val guard: Guard,           // 動作前必須成立的條件
    val post: PostCondition,    // 動作後必須成立（可驗證）
    val ok: Int, val fail: Int, // 貝氏統計
    val p95Ms: Int
)
```

**守衛類型**（全部可由無障礙树 O(1) 檢查）：

| Guard | 意義 |
|---|---|
| `ElementPresent(selector)` | 目標元素存在且可見 |
| `Capability(selector, SET_VALUE)` | 該元素具備某能力（元件能力圖譜） |
| `Package(pkg)` | 前景套件 |
| `NotNegative(edgeId)` | 該邊未被標記為禁區 |

**後置條件類型**（見 S3）：`SpineChanged` / `ElementAppeared(sel)` / `ValueIncreased(sel, δ)` / `PackageChanged` / `TextPresent(tok)`。

### 3.4 編譯流程（離線、增量、可中斷）

```
每 N 個新軌跡 觸發一次增量編譯：
  1. 正規化：把所有 sigsBefore/After → MinHash 節點
  2. 併邊：同 (from, op, selector) 合併，累加 ok/fail（Beta 後驗）
  3. 疊化：partition refinement 合併等價節點
  4. 剪枝：ok+fail < 2 且超過 14 天未再現 → 降級為「候選邊」
  5. 落盤：依 nodeBudget/edgeBudget（§3.7）淘汰，保留「最難重新發現」的邊
```

**編譯成本**：500 節點 / 2,000 邊的一次全量編譯 < 50ms（純 Kotlin，無模型）。
**觸發時機**：任務結束、螢幕關閉、服務空閒（`Handler.postDelayed` 低優先）。

### 3.5 執行：查表 + 檢查點

```kotlin
fun step(state: Int, goal: PostCondition): Edge? {
    val candidates = edges.filter { it.from == state && it.guard.ok() && it.notNegative }
    return candidates.minByOrNull { c(it) }   // 最短路的一步
}
```

**極限目標**：已知路徑的每步成本 ≤ 30ms（1 次簽名比對 + 1 次選擇器解析），
且**決策次數/任務 ≤ 2**（只有起點與終點需要「真感知」，中間全是查表＋驗證）。

### 3.6 失敗退化

- 圖未命中 → 退回現有 L1→L3 管線（成本不變，只是慢）
- 邊守衛不成立 → 跳過該邊，若無邊可走 → 重規劃（S4）→ 再不行 → 分類器
- 編譯結果異常（節點數暴增）→ 自動暫停編譯，保留原始軌跡

### 3.7 節點預算：依 App 複雜度自適應（**純程式，無 AI**）

#### 3.7.1 原則

> **預算 = f(已觀測複雜度)**，不是常數；所有計算都是整數運算與查表，
> **同一份軌跡必得同一份圖**（可審計、可寫成回歸測試）。

為什麼不能用常數：
- 常數取小 → 複雜 App（地圖／電商／社群）被頻繁淘汰，圖永遠長不完整
- 常數取大 → 簡單 App（計算機、計時器）白白佔記憶體，查詢也變慢
- 不同裝置（低階 4GB / 高階 12GB）記憶體預算差一個數量級

#### 3.7.2 五個測量量（全部來自既有資料，總成本 < 1ms）

| 符號 | 意義 | 來源 | 為什麼代表複雜度 |
|---|---|---|---|
| **V** | 已正規化的不同狀態數 | MinHash 聚類計數 | 頁面越多 → App 越大 |
| **T** | 已觀測的不同轉移數 | 軌跡去重 | 分支越多 → 越複雜 |
| **D** | 已用到的細分動作物種數 | `FineOp` | 需要越多操作型態 → 介面越豐富 |
| **K** | 不同頁面骨架數（class 家族集合） | 簽名骨架 | 結構多樣性（列表/表單/播放器…） |
| **P** | 每頁節點數的中位數 | 感知統計 | 單頁密度 |

#### 3.7.3 分級表（**放在資料檔，不寫在程式裡**）

`assets/open_source_ai_databases/ui_graph_budget_policy.tsv`

| tier | min_states | min_edges | min_skeletons | node_budget | edge_budget | ttl_days |
|---|---|---|---|---|---|---|
| SIMPLE | 0 | 0 | 0 | 32 | 160 | 30 |
| STANDARD | 24 | 80 | 3 | 64 | 384 | 30 |
| COMPLEX | 96 | 400 | 6 | 128 | 768 | 21 |
| HUGE | 320 | 1400 | 10 | 256 | 1536 | 14 |

分類演算法（純程式，O(級別數)）：

```
baseTier = argmax_tier { V ≥ min_states(tier) ∧ T ≥ min_edges(tier) }
kTier    = argmax_tier { K ≥ min_skeletons(tier) }        # K 只抬升下限
tier     = max(baseTier, kTier)
```

**為什麼 K 不當硬門檻**：有些 App 頁面很多但型態單一（例如聊天室只有列表），
若把 K 當必要條件會把它低估；反之型態多樣的 App 至少該有較高預算。
因此 **V/T 決定基礎級別，K 只能往上抬**。（此修正由 M2 的效能測試暴露：500 個互斥頁面
若只有一種姿態，會被誤判成 SIMPLE。）

**第一次編譯**（沒有歷史）→ 直接採用分類結果，**不套用 3 次滯迴**；
滯迴只用於「已有圖之後的升級」，避免新 App 前三次被過度裁切。

**裝置縮放（純規則，非 AI）**：低階機（RAM < 4GB 或核心 ≤ 4）自動降一級；
`HUGE` 為硬上限，避免單機記憶體與查詢延遲失控。

#### 3.7.4 兩個防震盪機制

| 機制 | 規則 | 目的 |
|---|---|---|
| **升級滯迴** | 連續 3 次編譯都達到下一級門檻才升級 | 避免一次偶然的深層探索就撐大預算 |
| **降級條件** | 連續 30 天使用量 < 預算的 40%，且仍達目前級門檻 → 降一級 | 避免長期佔用 |

#### 3.7.5 淘汰策略：丟「最容易重新發現的」，不是丟最舊的

```
keepScore(edge) = 使用次數 × Beta 成功率 × 新鮮度 / 重建成本

重建成本(edge) = 從最近的「常見頁面」到該邊的最短步數（BFS，純圖演算法）
```

- 保留「**難重建**」的邊（例如藏在三層選單裡的功能）
- 丟掉「隨便再走一次就會回來」的邊（例如首頁的搜尋框）
- 同分時以 edge key 字典序決勝 → 完全可重現

#### 3.7.6 冷啟動

新 App 還沒有任何資料時，用「**設計系統指紋**」（class 家族集合）找同指紋的既有 App，
借用其 tier 當初始預算（`min(SIMPLE+1, 借用來源的 tier)`），避免一開始就把預算開到最大。

#### 3.7.7 為什麼這是「純程式」

| 環節 | 手法 | 是否含 AI |
|---|---|---|
| 狀態聚類 | MinHash + 門檻比較 | 否 |
| 分級 | 查表 + 整數比較 | 否 |
| 滯迴 | 計數器 | 否 |
| 淘汰 | BFS 重建成本 + 整數排序 | 否 |
| 裝置縮放 | RAM/核心數規則 | 否 |

**沒有模型、沒有隨機、沒有學習率**；同一輸入必得同一輸出，可直接寫成單元測試。

#### 3.7.8 全域預算池（單機總量上限）

per-app 預算之外，再加一層「全域上限」，避免 20 個 App 各自吃滿預算：

```
總量上限：旗艦 2MB、中階 1.5MB、低階 1MB（依 RAM 與 App 數量，純規則）

weight(pkg) = 近 30 天使用次數 × 成功率
alloc(pkg)  = clamp( nodeBudget(pkg) × weight / Σweight,
                     nodeBudget(pkg) × 0.5,
                     nodeBudget(pkg) )
```

超出總量時，依 `health × weight` **由低到高**整張淘汰（可重建），不影響高頻 App。

#### 3.7.9 App 更新時的差分繼承

`versionCode` 變更時不要整張丟掉（那會讓使用者「一夜回到解放前」）：

```
1. 逐邊重新解析選擇器：viewId → 角色+文字 → 座標
2. 解析成功的邊：保留統計，成功率打 0.8 折（保守）
3. 解析失敗率 > 40% → 視為大改版：整張標記 STALE，退回分類器，背景重建
```

#### 3.7.10 測試規格（把「純程式」變成可驗證的契約）

| V | T | K | 裝置 | 期望 tier | nodeBudget |
|---|---|---|---|---|---|
| 0 | 0 | 0 | 旗艦 | SIMPLE | 32 |
| 30 | 100 | 3 | 旗艦 | STANDARD | 64 |
| 120 | 500 | 7 | 旗艦 | COMPLEX | 128 |
| 400 | 1600 | 12 | 旗艦 | HUGE | 256 |
| 400 | 1600 | 12 | 低階（RAM<4GB） | COMPLEX | 128 |
| 30 | 100 | 3 | 低階 | SIMPLE | 32 |

另外三條必測：

1. **滯迴**：連續 2 次達標不升級；第 3 次才升級
2. **降級**：30 天低使用且未達門檻 → 降一級
3. **重現性**：同一份軌跡 → 同一份 `sha256(automaton_json)`

## 4. 子系統 S2：負向知識（Negative Knowledge）

### 4.1 原則

> **每一次失敗都必須留下結構化的痕跡，而且永遠不再重犯。**

現有黑名單是「短期、單視窗、記憶體」；這裡升級為**持久、有型別、可參與規劃**的負邊。

### 4.2 負邊型別

| 型別 | 觸發 | 語意 | 生命週期 |
|---|---|---|---|
| `NO_EFFECT` | 動作後簽名不變 | 這條邊不存在 | 30 天（或直到成功一次） |
| `WRONG_EFFECT` | 跑到非預期頁 | 這條邊有毒 | 永久（除非人工解除） |
| `BLOCKED` | 安全閘門拒絕 | 不允許走 | 永久 |
| `TIMEOUT` | 動作卡住 | 這條邊太慢/不穩 | 7 天 |
| `AMBIGUOUS` | 出現多義目標 | 需要澄清才能走 | 直到澄清成功 |

### 4.3 負邊的作用（四處）

1. **規劃**：A* 直接跳過負邊（等同移除），不必等它失敗
2. **打分**：同 `(pkg, selector)` 的負邊計數 → 降權（取代現在的 `ActionTelemetry`）
3. **探索**：負邊是「已探索過」的證據，避免重複探索（S5）
4. **自我診斷**：負邊密度高的頁面 = 高風險頁（可提示使用者）

### 4.4 極限做法

- **組合負邊**：若 `s --a--> t` 失敗，且 `t --b--> u` 也失敗，自動推論 `s --(a,b)--> u` 為負（深度 2 的傳遞閉包）
- **條件負邊**：同一條邊在 A 條件下成功、B 條件下失敗 → 記錄「守衛否定式」，只在條件成立時才視為負
- **負邊遺忘曲線**：`weight = exp(-Δt/30d)`，避免一次偶發失敗永久禁用一條好邊

### 4.5 驗收

| 指標 | 定義 | 目標 |
|---|---|---|
| 重複錯誤率 | 同一 (pkg, 頁面, 動作) 再次發生失敗的比例 | < 5% |
| 負邊命中 | 被負邊提前阻止的失敗次數 | 每次任務 ≥ 0.3 次 |
| 誤禁率 | 好邊被誤標為負的比例 | < 2% |

## 5. 子系統 S3：目標編譯器（Goal → Postcondition）

### 5.1 為什麼要換掉「目標文字」

現在的做法是「把指令文字和每個候選文字比相似度」。問題：
- 「把亮度調高」→ 沒有任何元素文字像它（真實踩過）
- 「搜尋 invoice」→ 列表項目不會含這個詞（是搜尋結果，不是同義詞）

**極限做法**：把指令編譯成**可驗證的後置條件**，決策目標從「選最像的元素」變成「選最可能達成條件的動作」。

### 5.2 後置條件 DSL（極簡、可組合）

```
post := SPINE_CHANGED
      | ELEM_PRESENT(selector)
      | ELEM_ABSENT(selector)
      | VALUE_INC(selector, δ) | VALUE_DEC(selector, δ)
      | VALUE_EQ(selector, v)
      | TEXT_PRESENT(tokens)
      | PKG_EQ(pkg) | PKG_NE(pkg)
      | ALL(post, post) | ANY(post, post)
```

### 5.3 編譯規則（資料驅動，不寫死）

| 指令樣式 | 後置條件 | 依據 |
|---|---|---|
| 「打開 X」 | `PKG_EQ(pkg(X))` | App 元資料庫 |
| 「搜尋 X」 | `ELEM_PRESENT(LIST_ITEM) ∧ TEXT_PRESENT(X)` | 動作詞 + 詞庫 |
| 「把 Y 調高」 | `VALUE_INC(Y, δ)` | 元件能力圖譜（SET_VALUE 家族） |
| 「開啟/關閉 Z」 | `SPINE_CHANGED ∧ 元素狀態改變` | 開關能力 |
| 「回到上一頁」 | `SPINE_CHANGED ∧ 非目標頁` | 導覽語意 |
| 「點第 N 個」 | `ELEM_PRESENT(列表項) ∧ 位置=N` | 量詞資料庫 |

**推導式反推**（冷啟動時用）：從成功軌跡的最後一幀反推 postcondition
（例：TAP 之後新出現的列表項 → `ELEM_PRESENT(LIST_ITEM)`），存進資料表供下次使用。

### 5.4 決策變成控制問題

```
action* = argmax_a  P(post 成立 | s, a) − λ·cost(a)
P(post|s,a) 由 (i) 該邊的 Beta 後驗 與 (ii) 後置條件的靜態可滿足性 共同估計
```

### 5.5 極限做法

- **多目標合成**：一句話多個子句 → `ALL(post1, post2, …)`，規劃器一次解
- **條件後置**：「如果有彈窗先關掉」→ `ANY(ALL(POPUP_ABSENT, goal), ALL(goal, POPUP_ABSENT))`
- **軟後置**：允許 `post` 失敗但「部分達成」（例如搜尋有結果但沒開信），用於部分完成策略

### 5.6 驗收

| 指標 | 目標 |
|---|---|
| 後置條件可驗證率 | ≥ 90% 的任務能編譯出可驗證條件 |
| 任務成功判定準確度 | 誤報成功 < 2%（現況已知有過假成功） |
| 編譯耗時 | < 5ms/指令（純查表） |

## 6. 子系統 S4：規劃器（A* + 學習成本 + D* Lite 重規劃）

### 6.1 標準 A*

```
f(n) = g(n) + h(n)
g(n) = Σ 邊成本（延遲 + λ·失敗懲罰）
h(n) = 啟發式：頁面相似度距離（MinHash Jaccard 的補數）
```

**啟發式合理性**：頁面越不像目標頁，樂觀成本越高 → 可採納（admissible）。

### 6.2 學習型邊成本

每一條邊用 **Beta 後驗**估計成功率：

```
α = ok + 1,  β = fail + 1
P(success) = α / (α + β)
c(edge) = p95Ms / 1000 + λ · (1 − P(success))，λ = 3.0
```

**為什麼用 Beta**：樣本少時自動趨近 0.5（不亂相信），樣本多時收斂到真實值；比固定懲罰更穩。

### 6.3 即時重規劃（D* Lite 概念）

執行中某條邊失敗 → 不必從頭重算，只更新受影響子圖的 g 值（局部修復）。
**極限目標**：單次重規劃 < 5ms。

### 6.4 極限做法

- **層級規劃**：把圖依「頁面類型」聚類成超節點（首頁/列表/詳情/表單），先粗規劃再細化 → 規劃複雜度從 O(E log V) 降到 O(超節點數² + 局部)
- **目標導向剪枝**：只展開 `h(n) < 當前最佳解` 的節點
- **多目標路徑**：一次解「先做 A 再做 B」的 TSP 變體（子句 ≤ 4 時用 DP）
- **不確定性規劃**：以風險敏感成本 `c + κ·σ`（κ 可調，保守/激進）

### 6.5 驗收

| 指標 | 目標 |
|---|---|
| 規劃耗時（500 節點） | < 10ms |
| 規劃成功率（圖上有解時） | ≥ 98% |
| 重規劃耗時 | < 5ms |

## 7. 子系統 S5：主動探索（Coverage-driven Bandit）

### 7.1 現況：只學使用者走過的路

陌生 App 首次成功率 50–60% 的天花板，本質是「沒走過的路永遠不會被發現」。

### 7.2 極限做法（三層護欄）

```
探索只在：充電中 ∧ 螢幕關閉 ∧ 時間在允許區間 ∧ App 在白名單
每輪預算：≤ 3 分鐘、≤ 40 個動作
絕對禁區：輸入框、付款、刪除、權限對話框、設定的危險項
```

### 7.3 選點策略：用「資訊增益」而不是亂逛

```
UCT(edge) = 邊的成功率樂觀值 + c·√( ln N(狀態) / N(邊) )
選擇準則：優先「沒走過（N=0）」→ 其次「走過但樣本少」→ 最後「成功率高」
```

**與 MCTS 的差別**：MCTS 是「為了完成任務」而搜；這裡是「為了補圖」而搜，
目標函數是 **覆蓋率**（新增邊數 / 探索動作數），不是任務成功。

### 7.4 影子執行（不實際點的驗證）

對已規劃出的路徑，先在「記憶體中的圖」上模擬，檢查守衛是否可能成立；
只有全部通過才落到真機。**風險**：圖與現實不同步 → 用「檢查點驗證」補救（只驗關鍵 2–3 步）。

### 7.5 極限做法

- **被動探索**：使用者自己操作時，被動記錄成邊（已有 `PassiveRecordPolicy`，目前只記錄、不編譯）
- **引導式探索**：只探索「與已知任務相關」的子圖（例如使用者常用「搜尋」，就優先補搜尋路徑）
- **遺忘**：超過 30 天未用且成功率低的邊 → 刪除，控制圖大小

### 7.6 驗收

| 指標 | 目標 |
|---|---|
| 圖覆蓋率（白名單 App） | 首頁 + 前兩層 ≥ 80% |
| 探索誤操作率 | 0（禁區硬阻斷） |
| 陌生 App 首次成功率 | 50–60% → ≥ 75% |

## 8. 子系統 S6：跨 App 同構遷移（Zero-shot Transfer）

### 8.1 觀察

Material / AndroidX 的 App 有大量同構結構：
「工具列 + 搜尋框 + 列表 + 底部導覽」的骨架幾乎一模一樣。

### 8.2 做法：以「能力 + 用途」做圖同構映射

```
node_sig = ( 頁面類型, 容器骨架 )
edge_sig = ( op, 目標能力, 用途分類 )
```

若 App X 的 `edge_sig` 與 App Y 的相同 → 把 X 的邊「借」給 Y，標記為 `BORROWED`（成功率信賴度打折 0.6）。

**借邊的使用順序**：自家邊 → 借用邊 → 分類器。

### 8.3 極限做法

- **設計系統指紋**：以元件的 class 家族組合做指紋（Material3 / Material2 / 自繪），同指紋的邊可直接繼承
- **失敗回饋**：借用邊失敗一次即降權，失敗三次永久移除
- **型別對齊**：能力 ∩ 用途 的集合必須完全相同才允許借用（避免把「音量滑桿」的邊借給「播放進度」）

### 8.4 驗收

| 指標 | 目標 |
|---|---|
| 借用邊首次成功率 | ≥ 60% |
| 陌生 App 首步正確率提升 | +10pt 以上 |

## 10. 子系統 S8：安全型別系統（編譯期拒絕，不靠執行期閘門）

### 10.1 現況

安全是「派發前檢查」（`SafetyGate.evaluate`），屬於執行期防護——代表危險動作已經被規劃出來了。

### 10.2 極限做法：把安全變成「型別」

```
Edge 的型別 = (能力, 用途, 風險等級)
風險等級 ∈ { SAFE, CONFIRM, BLOCK }
規劃器只接受 SAFE 的邊；CONFIRM 的邊必須有人工確認才進入可執行集合。
```

**編譯期檢查**（建邊時就判定）：

| 規則 | 判定 |
|---|---|
| 目標位於付款/刪除語意的頁面 | BLOCK |
| 目標是權限對話框的允許按鈕 | BLOCK |
| 目標是輸入框且指令無對應 payload | BLOCK（避免亂打字） |
| 目標是唯讀元件卻要 TAP | BLOCK（元件能力圖譜） |

好處：**危險邊永遠不會出現在規劃結果裡**，執行期閘門退化成第二道保險。

### 10.3 通用性修補（順手要做）

- `permissioncontroller` 套件名目前在兩個檔案各寫死一次（AOSP + Google 兩種）→ 搬到 `system_safety_packages.tsv`，並補上 OEM 變體

## 13.2 P1 優化：多步導航 + 編譯去抖（2026-11）

### 多步導航

原本只敢跳「1 步 TAP」。現在改成整段導覽：

```
規劃 plan（1~4 步）
  → 逐步執行：定位選擇器 → 派發 → 重新感知
  → 每步驗證「是否真的走到預期狀態」（MinHash 相似度 ≥ 0.50）
  → 未抵達：記 WRONG_EFFECT 負邊，中止整條計畫（不硬走下一步）
  → 導覽全部成功：**不 return true**（導覽 ≠ 完成），回到正常決策在目標頁完成任務
  → 每目標最多 4 跳（避免在同一頁反覆導覽）
```

三個安全設計：
1. **導覽與完成分離**：只要還在「移動」就不算任務完成，避免假成功。
2. **逐步驗證**：不是「相信圖」，而是每跳都用量到的簽名確認。
3. **失敗即負邊**：走錯一次，該邊永久降級，下次規劃自動繞開。

### 編譯去抖

```
需要編譯 ⇔ 沒有既有圖
        ∨ 累積新步數 ≥ 12
        ∨ 距上次編譯 ≥ 5 分鐘
```

理由：每個任務都重編＋寫檔會浪費 flash 與電量；但間隔太久圖會落後。純函式、可測（`AutomatonCompilePolicy`）。

驗證：**312 項 / 0 失敗**（本輪 +6）。

## 13.4 效率與準確度（2026-11）

這一輪只做「能直接量到效果」的兩件事。

### 效率：感知幀重用

Agent 在「被拒絕 → 升級 → 重試」與「多步導覽驗證」時，常對**完全沒變的畫面**重複做完整感知（採集 ~200ms + 打分 ~90ms）。

```
可重用 ⇔ 同 App ∧ 同視窗 ∧ 同結構指紋（ambient spine）
        ∧ 期間無任何 TYPE_WINDOW_CONTENT_CHANGED 事件
        ∧ 距上一幀 ≤ 1500ms（必須小於事件保留窗口 2000ms）
```

- 純函式 `FrameReusePolicy`；快取由服務持有
- 關鍵安全性：**事件是唯一真相**——有事件就重採集，不靠猜
- 日誌：`WAE_CACHE frame reused … age=…ms`

### 準確度：目標完成驗證

原本的成功判定是「動作契約 APPLIED + 因果歸因有效」，但那只能證明「畫面對動作有反應」，不能證明「使用者要的事發生了」。新增 `GoalVerifier`（純規則）：

| 動作 | 驗證條件 |
|---|---|
| 啟動／直達 | 前景套件 == 目標套件 |
| 輸入／替換（**強制生效**） | 輸入內容出現在頁面（去空白標點、不分大小寫）；否則看結構是否改變，兩者皆無 → 失敗 |
| 返回 | 結構改變 **或** 套件改變 |
| 數值調整 | 派發時已讀回 RangeInfo 驗證 |
| 點擊／送出／捲動 | 結構指紋改變 |
| 等待 | 直接通過 |

- 目前**只對輸入類強制生效**（最常見的假成功：把字打進錯誤的框仍算成功）
- 其餘先只記錄 `WAE_VERIFY goal=… ok=… reason=…`，等累積數據再決定是否升級為強制

驗證：**338 項 / 0 失敗**（本輪 +13）。

## 13.5 S25 事件驅動增量感知（2026-11）

### 做法

```
事件（TYPE_WINDOW_CONTENT_CHANGED）→ 記錄髒區（最多 4 塊；超過就標記強制全量）
下一幀感知：
  ├─ 同 App ∧ 同視窗 ∧ 同結構指紋 ∧ 髒區 ≤ 35% 面積 ∧ 距上次全量 ≤ 1.2s
  │    → 只走「與髒區有交集」的子樹（祖先因為包含髒區仍會被走訪）
  │    → 再把「髒區以外的舊候選」合併回來（以 nodeStableSig 去重）
  └─ 否則 → 全量（行為與舊版完全一致）
捲動 / 視窗切換 / 髒區過多 → 強制全量
```

### 三個安全設計

1. **只對 TAP 目標啟用**：被沿用的舊候選沒有 live node 參照，TYPE/ADJUST_VALUE 需要節點讀寫屬性 → 那兩類一律全量。
2. **定期全量校驗**：距上次全量 > 1.2 秒就強制重走一次，避免增量誤差累積。
3. **判斷失敗就往保守倒**：沒有髒區、髒區太大、指紋不同、事件缺失 → 全部退回全量。

### 實測（真機，Gmail 兩個目標的任務）

```
WAE_VERIFY goal='點開第一封' kind=TAP ok=true reason=SPINE_CHANGED
```

## 13.8 M4：疊化與橋邊保護（2026-11）

### 疊化（bisimulation）

```
s ≡ t  iff  出邊標籤集合相同，且所有對應後繼都在同一等價類
```

- partition refinement，最多 20 輪，收斂即停
- 合併後指紋 = **各成員逐通道取最小**（MinHash 聯集語意）→ 合併節點與任一成員都相似
- 邊依 (from, op, selector, to) 去重並累加 ok/fail/lat，p95 取 max
- 少於 48 節點直接跳過（計算成本 > 收益）

**實測**（JVM）：
```
重複頁面模板：128 → 2 節點（64.0×），1.71ms
純鏈狀圖：    252 → 252（1.0×，無等價節點，正確不合併）
```

### 橋邊保護

淘汰（§3.7.4）可能把圖切成孤島 → 規劃回報無解。
現在淘汰後檢查最大連通元件覆蓋率，< 80% 就從「淘汰前的全部邊」中補回**成本最低**的橋邊，直到覆蓋率達標（最多 8 次）。

### 可驗證性

- 疊化**不破壞可達性**：測試直接驗證「疊化後仍能規劃 A→D」
- 疊化**可重現**：同一輸入兩次疊化 sha 相同
- 開關：`AutomatonCompiler.REDUCTION_ENABLED`（關閉即回 M2 行為）

驗證：**374 項 / 0 失敗**（本輪 +8）。

  - CLASS 回退先剔除導覽型列，再按證據分數排序；決策原因會印 `evidence=…`

### ADJUST payload 被導覽詞污染

- 舊：「進入顯示設定把亮度調高」→ payload `進入顯示 亮度`
- 修法：`GrammarParticles.stripLeadingDirections()` 去掉開頭的 進入/打開/前往/到/在/從
- 結果：payload → `顯示 亮度`（保留頁面名稱，有助定位；但不再把「進入」當目標）

### BACK 驗證收緊

- 舊：`BACK` 只記錄不強制 → `NO_CHANGE` 也自報成功（P7 假成功）
- 新：返回若「畫面與套件都沒變」且**不在桌面** → 判失敗（在桌面按返回本來就不會有變化）

### BOM 事故（基礎設施級）

盤點時發現 **28 個 TSV 帶 BOM**（PowerShell `Set-Content -Encoding UTF8` 造成）。
有 BOM 時第一行註解不會被 `startsWith("#")` 辨識，會被當成資料列——例如導覽詞表多了一條
「\ufeff# 內容項證據…」的假關鍵詞。已全部去除 BOM，並把「TSV 不可有 BOM」寫進 `AGENTS.md`。

驗證：**451 項 / 0 失敗**（本輪 +6）。

## 16. 第二層極限：把「編譯器」再推到「程式」

第一層（S1–S8）解決的是「不用每步看」，第二層解決的是「**連查表都不必**」。

### S9 推測執行（Speculative Execution）

動作還沒落地，就先預測下一個狀態並**預先解析下一步的選擇器**；動作一完成就直接派發。

```
predict: (s, a) → ŝ'     由邊統計取最高機率的後繼
prefetch: ŝ' 上最可能的下一條邊 → 預先快取節點引用與座標
```

- 命中：把「感知＋決策」的延遲完全藏進等待時間（等效 −100~200ms/步）
- 猜錯：丟棄預取結果，退回正常路徑（成本 = 一次無效快取，< 1ms）
- 極限：**連續 3 步的延遲預算可以合併成 1 步**

### S10 負空間儲存（Negative Space Representation）

不存「可行邊」，而存「不可行邊的補集」——因為在成熟圖上，**禁區遠比可行邊稀疏**。

- 儲存：每狀態只存 `blocked[]` + 「其餘皆可行」
- 查詢：`可行 = 全集合 − blocked`（位元運算，O(1)）
- 極限：SIMPLE 級別 ~2KB、STANDARD ~8KB、COMPLEX ~20KB、HUGE ~40KB（皆為壓縮後）

### S11 時間旅行（真機樹搜尋）

每步保存 256B 狀態快照 + 「回退動作」（BACK / 關閉彈窗 / 重進 App）。
失敗時可以回到第 k 步做**分支嘗試**，而不是從頭再來。

```
snapshot_k = (sigs_k, pkg, posture, 回退動作序列)
rollback(k) → 依序執行回退動作直到簽名匹配 snapshot_k
```

- 極限：單任務內可做 3–5 次分支（真機上的小型 MCTS）
- 風險：回退動作可能不可逆（已送出的訊息）→ 只對「純導覽」步驟開啟

### S12 學習型前向／反向模型（純 Kotlin，無神經網路）

從 `(s, a, s', post)` 學兩個極小的模型：

| 模型 | 形式 | 大小 | 用途 |
|---|---|---|---|
| 前向 `P(s' | s, a)` | 稀疏計數表 + 狀態聚類 | < 50KB | 規劃時預測後繼、支援 S9 預取 |
| 反向 `a = f(s, s')` | 決策樹（深度 ≤ 6） | < 100KB | 「我想從這裡到那裡，該按什麼」 |

**反向模型是關鍵**：它把「目標達成」變成「指定下一個狀態」，讓決策脫離語意比對。

### S13 能力蒸餾（把打分蒸餾成查表）

現況每步要跑 MiniLM（~90ms）。但**絕大多數頁面的「正確候選」其實固定**。

```
蒸餾：對 (頁面簽名 → 選中的 selector) 建立查表
命中條件：同一簽名 + 同一指令意圖 + 歷史 ≥ 3 次一致
推理：O(1) 查表，0 次 embedding
未命中：才走原打分
```

- 極限：embedding 呼叫次數從「每步」降到「每個新頁面一次」
- 量測目標：每任務 MiniLM 呼叫 ≤ 2 次

### S14 自我對抗任務生成（零人力的訓練場）

不用 LLM，用**資料庫組合**生成任務：

```
任務 = 動詞（動作詞庫）× 目標（當前頁面元素）× 修飾（量詞/數值表）
例：「搜尋 invoice 然後點第二封」「把音量調到 30%」
```

- 生成器只產生「圖上可驗證」的任務（後置條件可由 S3 編譯）
- 執行失敗的路徑 → 自動成為負邊 → 下一輪圖更乾淨
- 極限：無需人工標註，任務難度自動隨圖成長而提升

### S15 聯邦圖（Federated Automaton）

**這是成本結構的終極改寫**：別人買模型，我們共享「走過的邊」。

```
上傳：邊的雜湊（pkg_hash, 簽名_minhash, op, selector_hash, 成功率區間）
不上傳：畫面、文字、帳號、座標
合併：同鍵邊做貝氏合併（α,β 相加），個人資料不離開裝置
```

- 陌生 App 首次成功率的天花板，從「你走過多少」變成「大家走過多少」
- 隱私邊界：只傳統計量與雜湊，不可逆推畫面內容
- 極限：新裝置第一天的圖覆蓋率 ≈ 老裝置的 60–70%

### S16 路徑編譯成位元碼（真正的「程式」）

當某條路徑被執行 ≥ 10 次且成功率 ≥ 95%：

```
把 [邊1, 邊2, …, 邊N] 編譯成 bytecode：
  OP_GUARD(sel) / OP_TAP(sel) / OP_SETVAL(sel, expr) / OP_WAIT(post) / OP_VERIFY(post)
```

執行時只剩「取指 → 執行 → 驗證」，**沒有任何決策**。
- 極限：每步 ≤ 5ms；決策次數 = 0
- 失效：任何 OP_VERIFY 失敗 → 該程式降級，回退到圖規劃

### S17 零感知模式（Perception-free Mode）

對已編譯的路徑，**完全關閉截圖與 OCR**，只用無障礙事件確認畫面已變。

- 省電：每步從 30ms 降到 ~2ms（只做簽名比對）
- 風險：畫面變了但沒偵測到 → 用「事件驅動 + 逾時」補救
- 極限：長任務（30 步）的總感知成本 < 100ms

### S18 失敗根因標註（Failure Attribution）

每個失敗自動歸因到四類之一，形成可統計的錯誤模型：

| 根因 | 判定方式 | 對應修正 |
|---|---|---|
| 選擇器漂移 | 元素存在但 selector 不匹配 | 重建 selector（SelectorResolver） |
| 守衛錯誤 | 守衛成立但動作無效 | 收緊守衛條件 |
| 後置錯誤 | 動作成功但後置條件判錯 | 修正 GoalCompiler |
| 時序錯誤 | 逾時或過早驗證 | 調整 P95 等待 |

累積後可回答：「這個 App 的失敗 62% 是選擇器漂移」→ 優化方向自動浮現。

### S19 壓縮參數自我校準（離線網格掃描，非 AI）

MinHash 位數（32/64/128）、聚類門檻（0.6/0.7/0.8）都會影響「壓縮比 vs 召回」。
做法：每次全量編譯時，用**既有軌跡**做一次小規模網格掃描（≤ 12 組），
選「在召回不掉的前提下壓縮比最大」的參數，結果寫回資料檔。

- 成本：< 20ms（純位元運算）
- 可重現：固定候選集合與排序鍵
- 不是調參魔法：沒有梯度、沒有隨機

### S20 分層狀態（meta-node）

同一個「列表→詳情→返回」pattern 在 App 內可能重複出現幾十次。
用 **Weisfeiler–Lehman 圖指紋**（純圖演算法）偵測同構子圖 → 壓成一個 meta-node：

```
meta-node = ( 子圖的 WL 指紋, 出邊集合 )
查詢：先匹配 meta-node，再在子圖內展開
```

- 效果：節點數再降 2–5×，規劃在「功能層」先收斂
- 極限：規劃複雜度從 O(頁面數) 變成 O(功能區數)

### S21 熱路徑常駐

把使用頻率最高的 5 條路徑（邊序列 + 選擇器）預先載入記憶體、預熱選擇器快取。
- 首次進入該 App 的「熱路徑」查表成本 ≈ 0
- 純 LRU + 計數，不涉及模型

### S22 圖健康度分數與自動重建

```
health = coverage × freshness × success − negativeDensity
  coverage  = 已達狀態數 / 預算
  freshness = 邊的平均新鮮度（指數衰減）
  success   = 邊的 Beta 成功率加權平均
  negative  = 負邊數 / 邊數
```

- `health < 0.4` → 標記「需重建」，下次閒時做一次全量重新編譯
- 健康度可顯示給使用者（「這個 App 的模型已老舊」）

### S23 雙層 ID 與 O(1) 查表

```
stateId  = u64（MinHash 聚合）
edgeKey  = u128 = ( stateId << 64 ) XOR ( op << 56 | selectorHash )
```

- 查表：開放定址雜湊，無鏈結、無配置 → 單次查詢 < 100ns
- 碰撞處理：同 key 但 selector 不同 → 二級驗證（字串比對）

### S24 可重現性與差分回歸

- 同一份軌跡 → 逐位元相同的圖（`sha256(automaton_json)` 固定）
- 每次編譯記錄 hash；CI 用固定語料驗證「改程式不能偷偷改變圖」
- 這讓「優化」與「回歸」可被機器判定，不靠人眼

### S25 事件驅動狀態維持（Event-sourced State）

現況每輪都重掃整棵樹。極限做法：用 `AccessibilityEvent` 的變化範圍**增量維護**簽名。

```
onContentChanged(source) → 只重算 source 子樹的簽名 → MinHash 增量更新
無事件時（靜止頁）→ 直接沿用上一次簽名，零掃描
```

- 效果：感知成本從 O(樹大小) 降到 **O(變化量)**；靜止頁 ≈ 0
- 風險：事件遺漏（部分 App 不回報）→ 每 10 秒或每次決策前做一次全量校驗

### S26 AOT 全路徑編譯（受目標語意約束）

不只編譯熱路徑：對「已達到的狀態 × 已編譯的後置條件」做**可達性分析**，
把可達且有意義的路徑全部預編譯成 bytecode。

- 限制：只編譯「到得了且後置條件可驗證」的路徑（避免組合爆炸）
- 上限：每 App ≤ 32 條編譯程式（超過按使用頻率淘汰）
- 效果：使用者第一次想做的事，可能已經預先編譯好

### S27 自我提問維護（Self-query Micro-tasks）

對「久未驗證」或「成功率下滑」的邊，自動生成**最小驗證任務**：

```
微任務 = 從當前 App 首頁走到該邊，執行一次，驗證後置條件，然後返回
成本預算：≤ 6 步、≤ 20 秒，只在充電＋螢幕關閉時
```

- 這是「圖的定期健康檢查」，用真機而非模擬
- 純規則觸發（TTL、成功率、健康度），無 AI

### S28 位元鄰接與 BFS（資料結構極限）

- 每個節點的出邊用 **bitset（256 bits）** 表示
- 最短路用 bitset BFS（每層用位元運算展開）→ 比指標追蹤快 10–20×
- 極限：500 節點的圖，最短路 < 0.3ms

### S29 能耗敏感規劃

把電量當一級成本：每種動作估一個耗電（手勢 > 點擊 > 等待；截圖 > 無障礙）

```
c(edge) = 延遲 + λ·失敗風險 + μ·耗電估計
μ 由剩餘電量決定：低電量時 μ 放大 3×（優先選「不用截圖」的路徑）
```

### S30 聯邦圖的悲觀合併與版本化

跨使用者合併時**不能取平均**（會讓壞邊看起來很好）：

```
合併規則：α,β 相加；版本不同時以「成功率較低者」為準（悲觀合併）
衝突（同一邊一成一敗且樣本都 ≥5）→ 標記 CONFLICT，只在本機重新驗證後才採用
```

| 層 | 目標 | 代表手法 |
|---|---|---|

## 16.2 誠實：哪裡已經到底了（不可再極限）

推到底之後要承認理論下限，否則就是自欺：

| 項目 | 理論下限 | 為什麼不可能更低 |
|---|---|---|
| 感知單步成本 | ~2ms（一次簽名比對／一個事件） | 要確認「畫面已變」至少需要一次比對；完全 0 等於盲操作 |
| 決策次數 | 1（選擇哪條程式） | 指令進來時仍需與目標比對一次 |
| 已知任務成功率 | ~98%（非 100%） | 畫面時序、動畫、網路載入仍有不可控因素 |
| 陌生 App 首步成功率 | ~70–80% | 沒有任何先驗時，首步就是猜；除非有聯邦圖 |
| 遊戲／Canvas 類 App | 不適用 | 無障礙树與文字都不可觀測，只能靠視覺，成本無法壓低 |
| 指令歧義 | 必須問 | 「把那個打開」在沒有人類上下文時不可解 |

**結論**：這套架構的極限不在「算得更快」，而在「把不確定性搬到離線、把重複性編譯成程式」。
真正不可壓縮的只有三件事：**一次確認、一次選擇、一次詢問**。

## 18. 如何證明這套值得（消融實驗設計）

沒有量測的優化都是自我感覺良好。每個子系統都必須能單獨量出邊際效益。

### 18.1 開關矩陣（Ablation）

| 組別 | 開啟 | 目的 |
|---|---|---|
| A（基準） | 全部關閉（= 現況 V2.6） | 對照組 |
| B | +S2 負邊 | 負邊的邊際效益 |
| C | B +S1 自動機 | 查表 vs 分類器 |
| D | C +S4 規劃 | 規劃 vs 貪婪 |
| E | D +S3 後置條件 | 目標編譯的效益 |
| F | E +S13 蒸餾 + S17 零感知 | 成本下降幅度 |
| G | F +S15 聯邦 | 陌生 App 提升 |

### 18.2 每組要量的六個數字

1. 任務成功率（四級難度分開）
2. 每步中位／P95 延遲
3. 每任務感知調用次數
4. 每任務 MiniLM 呼叫次數
5. 失敗歸因分佈（S18 的四類）
6. 圖覆蓋率與收斂速度（新增邊數/任務）

### 18.3 成本推導（為什麼結構性便宜）

```
分類器：Cost_task = N · (C_perceive + C_score + C_decide + C_act)
                   = N · (220 + 90 + 30 + 900) ms  ≈ N · 1.24s

編譯器：Cost_task = N · C_act + C_plan + K · C_verify
                   ≈ N · 0.9s + 10ms + 2 · 30ms
        差額      ≈ N · 0.34s   （N=20 時 ≈ 6.8 秒/任務）

VLM-per-step：Cost_task = N · (1500 + 網路) ms ≈ N · 1.5s + 費用
```

**結論**：我們的優勢不在「比較快」，而在「N 增加時成本不成長」——
同樣 30 步的任務，他們付 30 次推論，我們付 0 次。

## 19. 會讓這套崩掉的情況（極限的風險）

| 風險 | 為什麼致命 | 緩解 |
|---|---|---|
| **圖中毒** | 惡意/異常 UI 讓邊統計偏斜 | 每邊最少 3 次樣本才可信；單次災難性失敗（WRONG_EFFECT）永久黑名單 |
| **狀態爆炸** | 圖節點線性成長到無法查詢 | bisimulation 疊化 + 每 App 60 節點上限 + 遺忘曲線 |
| **假成功** | 後置條件寫錯 → 圖學到錯的邊 | 後置條件必須「可從畫面驗證」；誤報成功 < 2% 為上線門檻 |
| **聯邦圖隱私爭議** | 使用者不信任 | 預設關閉；只傳統計量；可一鍵清除 |
| **過度自信** | 圖很舊、App 改版 | 邊的 TTL + 連續失敗 3 次自動關閉該 App 的自動機 |
| **維護複雜度** | 新增 8 個子系統 → Monolith 更肥 | S1 起就強制分檔；服務只保留「接線」 |

## 20. 誠實的邊界

1. **這套架構不會讓「完全沒人用過的 App」變萬能**——它只是把「走過一次」的價值放大到極致。
2. **首次成功率的提升來自探索與遷移**，兩者都有風險，必須嚴格護欄。
3. **VLM 仍然有它的位置**：圖完全沒有資料時，分類器（含視覺與 OCR）仍是唯一的起步方式。
4. **成本節省主要發生在「第二次以後」**——這正是與雲端 VLM Agent 的結構性差異。
5. 我們承諾的指標都會附「怎麼量」；沒有量測的數字不寫進對外文件。

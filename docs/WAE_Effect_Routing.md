# 極致創新：三個候選與我選的那一個

> 2026-11-17｜用途：判斷「下一代差異化」要押在哪裡。不是功能清單，是**架構主張**。

## 0. 先說結論

我選 **效果路由（Effect Routing）**：使用者說的是**結果**，不是 App；系統在多個 App／系統 API 之間挑一條路，並說得出為什麼。

理由：它同時吃掉三個痛點——廣度（不是「支援 N 支 App」而是「支援 N 種結果」）、效率（挑最少步的路）、信任（選路的理由可讀）。而且**不需要推翻 Gen-5**，是長在它上面的一層。

---

## 1. 三個候選（誠實評分）

| 候選 | 一句話 | 為什麼現在幾乎沒人做 | 對我們的價值 | 難度 | 要不要改架構 |
|---|---|---|---|---|---|
| **A. 效果路由** | 「傳照片給媽媽」→ 在 LINE／簡訊／郵件／系統分享之間挑最省又最穩的一條 | 主流是「一個 App 一個整合」（Siri/Google），或「你指定哪個 App」（VLM agent）；跨 App 選路要**本地歷史**才知道哪條穩 | ★★★★★ 廣度＋效率＋可解釋 | 中 | 加一層，不必推翻 |
| **B. 憑證式動作** | 每個動作執行前必須先有「憑證」：前提事實＋授權規則＋預期差異；驗不過就不准動 | 業界把可解釋性做事後 log；事前強制檢查會讓 demo 變慢、變醜 | ★★★★ 信任（敢給陌生人） | 中 | 加在 Executor 前 |
| **C. 差異感知（Reconciler）** | 不重讀整個畫面，只算「這一動改變了什麼」；驗證＝比對預期差異 | 主流 agent 每步重看整屏；把 UI 當 React 樹做 diff 的很少 | ★★★★ 效率（每步從 300–800ms 降到 30ms 級） | 中高 | 改 L0／驗證層 |

**B 和 C 都很好，但都是「把 A 做得更好」的配角**：A 決定做什麼，B 保證不做錯，C 讓它夠快。所以旗艦選 A。

---

## 2. 效果路由（A）長什麼樣

### 2.1 抽象改變

```
現在： 指令 → 效果（綁在一個 App 上）→ 手段 → 執行
之後： 指令 → 結果（Goal）→ 多條路（Route）→ 每條路內部才用效果／手段
```

- `Goal`：`SEND_MEDIA(照片, to=媽媽)`、`SEARCH(台北101)`、`TOGGLE(藍牙, off)`
- `Capability`：某個 App 對某類 Goal 的**本地證據**（嘗試次數、成功次數、平均步數）
- `Route`：`app → 步數 → 可靠度 → 分數`，附一句「為什麼選它」

### 2.2 分數怎麼算（全部可調、可解釋）

```
p        = (successes + prior) / (attempts + 2·prior)     // 拉普拉斯平滑，沒有資料時不吹牛
score    = p / (steps + 1)                                // 每多一步就扣分
若反例庫對 (goal, app) 有 BAN → 排除；有 LOWER → score × 罰分
```

沒有資料的新 App 不會因為「沒資料」就被判死，但也不會贏過有實績的路——這就是「越用越準」的來源。

### 2.3 為什麼這是「新物種」而不是優化

1. **廣度的度量換了**：從「支援幾支 App」變成「支援幾種結果 × 幾條路」。加一支 App 只加一條路，加一個**結果種類**才加一片。
2. **資料護城河是局部的**：哪條路在這台手機上穩，是這台手機的歷史；雲端只有群體平均。
3. **失敗會換路，不是重試**：同一條路失敗三次，路由器就把它降級，改走別條——這正是「任意 App」真正需要的行為。
4. **可解釋性天生**：選路的理由是一行數字，不是模型的一段話。

### 2.4 殺手級 demo（離線、飛航模式）

> 「把剛才那張照片傳給媽媽」
>
> 它列出四條路：
> `LINE 7 步 p=0.62`（上次分享面板卡住 2 次）／`簡訊 3 步 p=0.91`／`郵件 5 步 p=0.85`／`系統分享 4 步 p=0.74`
> 選簡訊，顯示「為什麼」；送出前確認。
> 若簡訊失敗 → 自動改走郵件，並記一筆反例。

這是主流助理做不到的：它們**不知道**自己上次在哪卡住，也沒有第二條路。

## 3. 跟現有架構的關係

```
L6 UI
L5 語音
L4 執行        Executor（不變）
L3.5 路由      ★ 新增：Goal → Route → 效果／手段
L3 求解        MeansSolver（不變）
L2 編譯        Intent → EffectGraph（S5）
L1 型別        Contract（不變）
L0 感知        Frame（不變）
```

路由器只多做一件事：**在效果之前多一層「用哪個 App 做」的決策**。其他層不動。

---

## 4. 怎麼驗（沒有數字就不算）

| 指標 | 定義 | 目標 |
|---|---|---|
| 選路正確率 | 選到的路 vs 事後最佳已知路 | ≥ 80% |
| 步數節省 | 同結果，路由 vs 固定預設 App | −25% |
| 換路成功率 | 首選失敗後，第二條路成功 | ≥ 70% |
| 解釋可讀性 | 陌生人看懂「為什麼選這條」 | ≥ 90% |
| 第二次更好 | 同結果第二次執行步數／時間 | 下降 |

第一版只需要 3 個結果種類（`SEND_TEXT`、`SEND_MEDIA`、`SEARCH`）× 3 支 App，就能看出方向對不對。

---

## 5. 風險

| 風險 | 徵兆 | 止損 |
|---|---|---|
| 路由是偽需求 | 使用者其實都想指定 App | 保留「指定 App」為硬約束，路由只在使用者沒指定時生效 |
| 資料太少算不準 | 前 20 次亂選 | 前 N 次用保守先驗（prior 大），且一律顯示「還在學」 |
| 跨 App 的確認地獄 | 每一步都要確認 | 只有 HIGH 風險與首次使用該路徑要確認 |
| 多一條路就多一個 bug | 每條路各有例外 | 每條路都必須是同一組效果／手段組出來的，不准有專屬程式碼 |

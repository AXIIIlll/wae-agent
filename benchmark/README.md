# 100 任務評測集

**這是本專案「等級宣稱」的唯一依據。** 沒有這份數字，任何「第一梯隊」的說法都是自嗨。

## 構成

| 難度 | 任務數 | 最低必要步數（實測） | 內容 |
|---|---|---|---|
| EASY | 30 | 1–2（中位 2） | 開 App、單次搜尋 |
| MEDIUM | 30 | 4–5（中位 4） | 搜尋 → 打開 → 返回 → 再操作 |
| HARD | 25 | 10–20（中位 13） | 多層導覽、篩選、滾動、寫入 |
| **EXTREME** | **15** | **32–35（中位 33）** | 跨頁多分支／多階段／含干擾與取消 |

100 個任務分布在 10 個 App 家族（mail / maps / video / social / shop / game / settings / browser / music / files）。

## 難度分級的明確邊界

**「步」的定義**：一次成功的介面動作（點擊／輸入／捲動／返回），不含等待與重試。
`min_steps` 欄位記錄「該任務達成的最低必要步數」，不是隨機長度。

| 難度 | 題數 | 最低必要步數 | 典型目標數 | 必要能力 | 逾時上限 | 通過率目標 |
|---|---|---|---|---|---|---|
| EASY | 30 | 1–2（中位 2） | 1 | 單一動作：啟動 App 或一次搜尋 | 40–50s | ≥ 95% |
| MEDIUM | 30 | 4–5（中位 4） | 2 | 搜尋 → 選取 → 返回；兩個頁面內完成 | 70–90s | ≥ 80% |
| HARD | 25 | 10–20（中位 13） | 3–4 | 多層導覽；需要捲動或條件篩選 | 150–240s | ≥ 60% |
| EXTREME | 15 | 32–35（中位 33） | ≥ 6 | 分支迴圈：多次搜尋／開啟／返回，且需容錯 | 360–400s | ≥ 30% |

**分級原則**：主軸是「必須成功的最少動作數」，次軸是「是否需要跨頁、是否跨 App、是否需要容錯重試」。
只要任何一項跨過下一級的主軸區間，就歸入該級；同級內不再細分。

## 判定規則

1. 以服務內部訊號為準（`lastTaskSuccess` + `taskRunSeq`），**不看畫面文字**：
   `WAE_EXEC taskResult=SUCCESS|FAIL seq=N`
2. 每題執行前先強制停止目標 App，確保從預設首頁（冷啟動）開始。
3. App 未安裝或無此功能 → 記為 `SKIP`，**不計入通過率**（避免虛增或虛減）。
4. **要求「說出看到什麼」的題目 → 記為 `SKIP`**（2026-11-23 使用者決定）。
   我們目前只有「手」沒有「嘴」：`在時鐘看世界時間`、`查看 USB 偵錯狀態` 這類題目，
   成功條件是能回報內容，而 App 沒有回答通道，跑幾次都只會是假失敗。
   這類題目在 TSV 第 6 欄標 `skip`、第 7 欄寫原因；要恢復只要把 `skip` 拿掉。
   目前標記：018、019、036、037、062、063、082。
   注意「導覽到某一頁」不算這類（例如 `查看通話紀錄` 只要畫面停在通話紀錄就成立），
   所以 025、038、046、052、055–058 仍列入計分。
4. 逾時未完成 → `FAIL`，並記錄最後一步的決策原因。

## 檔案

- `tasks.tsv` — 任務定義（可人工編輯；由 `tools/gen_benchmark_tasks.py` 生成，可復現）
- `results/<timestamp>.tsv` — 每次執行的原始結果
- `tools/run_benchmark.py` — 執行器

## 執行

```powershell
# 全部（約 2–4 小時，視 EXTREME 任務長度）
python tools/run_benchmark.py

# 先試跑 5 個，確認裝置與 App 狀態正常
python tools/run_benchmark.py --limit 5

# 只跑某一層（建議先 EASY → MEDIUM → HARD → EXTREME）
python tools/run_benchmark.py --tier EASY
python tools/run_benchmark.py --tier EXTREME

# 只跑指定任務
python tools/run_benchmark.py --id E02 --id M01
```

前置：手機已裝最新 APK、無障礙服務已啟用。執行器會用 `debug_command` 注入中文指令，
不需要 adb 支援中文輸入。

## 判讀方式

每次執行印出：

```
[12/100] M02 MEDIUM PASS  38.4s steps=4  ...
=== 摘要 ===
EASY    n=30  成功率= 93.3%  平均耗時=  22.1s  達到預期步深=28/30
MEDIUM  n=30  成功率= 66.7%  ...
HARD    n=25  成功率= ...
EXTREME n=15  成功率= ...     ← 這一層是「世界級」的門檻
```

**三個必看數字**
1. 各層成功率（EASY ≥95%、MEDIUM ≥80%、HARD ≥60%、EXTREME ≥30% 才算可宣稱第一梯隊）
2. 「達到預期步深」比例（= Agent 是否真的走完長鏈，而不是提早判定成功）
3. 平均耗時（EXTREME 常超過 2 分鐘，需注意逾時設定）

## 誠實提醒

- 目前任務由模板生成，**不代表真實使用者分布**；之後應以真實使用日誌加權
- EXTREME 任務含「按讚／加入購物車」等寫入動作，會經過安全閘門（可能需要人工確認），
  這些任務的失敗不完全是 Agent 能力問題，需分開統計
- 任務文字含 App 別名（地圖、gmail…）是**使用者口語**，不是程式資料

## 判定機制（2026-11-12 修訂）

舊版判定讀 UI 狀態文字是否含 `✓`，**不可靠**（狀態列會被下一則訊息覆蓋，成功也可能判成失敗）。

新版改用**確定性訊號**：
1. 服務在每次任務開始時 `taskRunSeq += 1`
2. 任務結束時寫入 `lastTaskSuccess = true/false`（整條任務所有步驟成功且未被取消才為 true）
3. 評測器輪詢這兩個值，不讀畫面文字

對應日誌：`WAE_EXEC taskResult=SUCCESS|FAIL seq=N`
